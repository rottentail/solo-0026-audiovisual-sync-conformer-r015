## 结论（先说结果）

按当前实现，**这个置信度不能代表“音画配对是否可信”**。它实际衡量的是“两个事件各自有多显著”，既不评估事件的唯一性，也不评估两者在时间上是否真的对应同一事件。在我用真实检测器跑出的合成素材矩阵里，它甚至出现反向表现：**错误配对拿到 1.000，正确配对因为画面闪光偏弱只有 0.188–0.613**。

本次只做评估，**未修改工作区任何文件**（`git status` 干净）；实验在 `/tmp` 的副本里用临时下载的 Go 1.23.12 工具链完成。

## 1. 置信度的实际含义

- 合并值：`confidence = (audio_prominence + video_prominence)/2`，三位小数（`internal/media/signal.go:34`）。
- 音频显著度：`min(1, log10(1+峰值/底噪)/2)`；峰值取**全片**窗口 RMS 最大值，底噪只取**文件开头 60 ms**（`signal.go:107-116`）。也就是说，第 40 秒的拍板声是拿片头 60 ms 来比。
- 画面显著度：`min(1, Δ/80)`，Δ = 全片最大帧亮度 − **全片中位数**（`signal.go:136-161`）。Δ ≥ 80 就饱和成 1.0，188 和 80 得分完全相同。
- 事件选择：音频选**第一个**满足“超过全局峰值 18%、前 4 个窗口里 ≥3 个安静”的起点（`signal.go:76-95`）；画面选**第一个**越过 `中位数+0.55Δ` 的帧（`signal.go:149-156`）。两者都与显著度无关。
- `drift_ppm`（`signal.go:29-33`）是 `offset/max(事件时刻)`，不是时钟漂移，标定素材 125 ms 会报 250 ppm；该字段目前不参与任何判定，但会出现在响应里。

所以它是有界的“响度/对比度分数”，不含唯一性、次优候选、跨模态一致性这三类配对证据。

## 2. 三类素材上的实测（真实 Go 检测器，视频帧 9 = 375 ms）

| 场景 | 检测结果 | 真实偏移 | 置信度 | 结果 |
|---|---|---|---|---|
| 标定：单拍板 500 + 强闪光 | a500/v375 | +125 | 1.000 | 正确 |
| 多次拍板：100 与 500 等强 | a100/v375 | +125 | **1.000** | **错配** |
| 多次拍板：100 弱 + 500 强 | a100/v375 | +125 | **1.000** | **错配**（弱拍板也过 18% 门限） |
| 对白 200 ms 起、拍板 500 | a200/v375 | +125 | **1.000** | **错配**（对白起音当选） |
| 对白从 0 开始、无安静前缀 | — | — | — | `audio onset was not found`，正确素材被判失败 |
| 片头 60 ms 很响 + 拍板 | a500/v375 | +125 | 0.576 | 正确但贴近 0.55 默认门限 |
| 同上 + 最小对比闪光 | a500/v375 | +125 | **0.188** | `low_confidence`，**正确配对被拒** |
| 整条持续变亮 16→216，无闪光 | a500/v750 | +125 | **1.000** | **错配**（把斜坡末段当闪光） |
| 变亮 + 中等闪光（帧 9=120） | a500/v791 | +125 | **0.875** | **错配**（闪光被斜坡盖过） |
| 两处等强闪光（帧 4、9） | a500/v166 | +125 | **1.000** | **错配** |
| 最小对比闪光（Δ=18） | a500/v375 | +125 | 0.613 | 正确，勉强过默认门限 |
| 亮底上的暗闪 | — | — | — | `insufficient contrast`，只认变亮 |

结论很清楚：**显著度饱和后，多次拍板、响对白、持续变亮都会产出“高置信度 + 错误偏移”**；反过来，正确的暗闪/弱闪素材会被压低甚至拒绝。

## 3. 阈值与最终音画结果的关系

判定链路在 `internal/service/service.go:112-147`，顺序是：

1. 检测出错 → `sync_detection_failed`（事件字段为空）。
2. `confidence < min_confidence` → `low_confidence`（默认 0.55，`domain/validation.go:17`）。
3. `|offset| > max_offset_ms` → `offset_exceeded`（默认 1000）。
4. 以上都通过 → `ready`。

关键点：

- **只有 `max_offset_ms` 与配对后果有关，但它只是幅度门限**。错配只要落在 1000 ms 内（实测 −275/−175/−250 全部通过）照常 ready。`min_confidence` 只能拦“不显著”，拦不住“显著但配错”。我实测了 `min_confidence` 从 0.55 到 1.0 的扫描：**正确标定对在恰好 1.000 时仍然通过**（比较是 `>=`），所以 1.0 也不能当“只接受确定配对”使用；>1.0 会被参数校验拒绝。
- **最终同步结果完全继承这一次配对**：ready 后 `offset` 原样进入 conform（`service.go:204`），`AlignAudio` 只做整数样本平移（`media/align.go:24-31`），产物里没有“配后复核”。阈值一旦放行了错配，交付包就是按错误偏移对齐的，receipt 还会如实记录这个错误偏移。
- **三个门限互相独立**：分析上限（可达 10000）与 conform 校正上限（默认 500）不是一回事，所以会出现“ready 但不可 conform”的分析。
- **失败记录仍暴露可用事件对**：`service.go:116-123` 在门限检查之前就写入了 `audio_event_ms/video_event_ms/offset_ms`，实测 `low_confidence` 响应里带着 `offset_ms:125, confidence:0.188`。这与 `PROJECT_SPEC` 的“failed … never exposes a usable event pair”不一致。调用方若只看置信度、不看状态，仍会拿到一对看起来可用的数字。
- 我验证了一个**看似合理但无效的复核方案**：先按 offset 对齐音频再重新检测。错配对也会得到 residual = 0（实测两次拍板、对白起音、双闪光、变亮全为 0），因为两个检测器会再次把同一批事件配到一起——这是自洽闭环，不是独立校验。

## 4. 提高错配识别能力的方案与代价

实测基线（单项上限：音频 8 MiB = 87.4 s 单声道 48 kHz，视频 24 MiB；`CGO_ENABLED=0`，单机，绝对值随机器变化）：完整 `AnalyzeSync` 在双上限约 **137 ms / 33 MiB 分配**，其中 `InspectVideo` 84 ms/25 MiB（逐帧复制，`y4m.go:58-60`）、`InspectAudio` 41 ms/8 MiB；检测本身很便宜（画面 7 ms、音频 6 ms）。也就是说**长素材的开销主要在解码+拷贝，不在检测算法**。

| 方案 | 新增配对证据 | 上限素材额外代价 | 内存 | 风险/说明 |
|---|---|---|---|---|
| A. 候选全收集 + 唯一性（次优/最优比、最小间隔） | 是否只有一个可信事件 | 87 s 音频 **0.16 ms** | O(候选数) | 最便宜；但直接比相邻局部极大值会因衰减尾巴失真（实测比 0.46–0.94），必须先做最小间隔/平台合并 |
| B. 多假设偏移投票（音频候选 × 画面候选） | 偏移共识、投票份额、至少一对佐证 | K·V 次比较；实测候选 ≲ 8–80，**可忽略** | 小 | 能把“无配对”“多配对”和“唯一配对”分开；比单一 earliest 规则可靠得多 |
| C. 画面因果阶跃检测（帧差而非绝对电平），抑制持续变亮 | 变亮≠闪光 | 单遍扫描 **3.5–18 ms** | ~0 | 需明确“单帧闪光是脉冲、持续变亮不是阶跃”；我试的严格阶跃规则会拒掉所有单帧闪光，参数要调 |
| D. 单遍流式亮度扫描，不再拷贝整帧后再检测 | — | 1200×96×54 **6 ms**；291×320×180 **18 ms** | ~0（省 25 MiB） | 比现状更便宜，可作为 A/B/C 的承载方式 |
| E. 音频局部自适应底噪（滑动中位数/百分位） | 响对白不再污染底噪 | **11.3 ms / 5.3 MiB**（可做成 O(1)） | 小 | 能修“片头很响导致正确配对掉到 0.188”，但仍无法区分对白起音与拍板 |
| F. 子带/谱平坦度区分“瞬态 vs 语音” | 直接针对“对白较响” | 估计 **50–150 ms**（需 FFT，未实测） | 中等 | 唯一真正针对语义的方案，但改动最大、需要新常量 |
| G. 包络域互相关（±1 s，5 ms 步长） | 整体波形一致性 | **11.4 ms** | ~0 | 与 A/B 可叠加；注意归一化 |
| H. 全采样互相关 | — | **1 s 搜索耗时 2.0 s** | 0 | 比现状慢约 15 倍，不建议 |
| I. 配后重检 | — | 1–2 ms | 小 | **不可用**：错配 residual 也为 0（见上） |

推荐优先级：**B（投票/共识）作为置信度主证据，A 作唯一性辅助，C+D 修画面侧，E 修音频底噪**；F 作为可选的下一阶段能力。A–E 在现有 24 MiB/1200 帧上限下的增量都在几十毫秒以内，远小于现有解码 137 ms，且 HTTP 写超时 90 s 有充足余量。需要提醒：当前上限决定了“长素材”主要是长音频（最长约 524 s@8 kHz）与小分辨率长视频（1200 帧@96×54 = 50 s）；高分辨率素材只能很短，所以按像素计的工作量天然被 24 MiB 封顶。

## 5. 应由交接方决定“保留哪些现有行为”

以下是需要交接方拍板的现有语义（我不代替决定）：

1. **`confidence` 字段的语义与兼容性**：是否保留“显著度均值”定义，还是改为共识分数；是否新增唯一性/歧义/检测器版本字段。
2. **`min_confidence` 的默认 0.55、取值 [0,1]、`>=` 比较**（恰好 1.0 会通过）是否保持不变。
3. **`max_offset_ms` 的幅度门限语义、1–10000 范围**，以及它与 conform `max_correction_ms`（默认 500）的独立关系。
4. **失败分析是否继续暴露事件对**：现状与 `PROJECT_SPEC` 文字冲突，需决定是清空字段还是修订规格。
5. **事件选择规则**：是否由“第一个起音/第一个越阈值帧”改为“共识/最近候选”；这会改动 `audio_event_ms`、`video_event_ms`、`offset_ms`，进而改动 bundle 与 receipt。
6. **标定工作流不变量**：`syncflowcheck` 依赖 500/375/125 与 confidence ≥ 0.55，是否保留。
7. **`drift_ppm`**：保留现状（非真实 ppm、未被使用）还是重定义/移除。
8. **幂等与终态**：分析身份包含 `(take_id, policy)`，收紧阈值必须换新 `analysis_id`；以及 `sync_detection_failed`、`low_confidence`、`offset_exceeded` 这些公开错误码是否新增。
9. **原子提交、每标识锁、失败 conform 不出包、receipt/bundle 摘要一致性**等既有不变量，建议无条件保留，但仍需交接方确认。

**一句话总结**：现有置信度只能说明“两个事件都够响/够亮”，说明不了“它们是一对”；阈值只能决定这份错误的偏移要不要被包装成审片包。要提升误匹配识别，最划算的路径是把“候选唯一性 + 偏移共识”变成新的置信度主证据（代价可忽略），画面侧改为阶跃检测并流式扫描（反而更省），音频底噪改为局部估计（十几毫秒）；其余保留项交由交接方定夺。
